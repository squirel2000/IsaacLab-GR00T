### Findings from section 4

- **The dataset needed no format conversion at all** — only the missing `meta/stats.json`. The original plan to convert v2.0→v2.1 would have *removed* the file the loader requires.
- **A modality config is mandatory for `GENERAL_EMBODIMENT`** despite upstream calling it "the slot `RLDX-1-PT` reserves for downstream fine-tuning" — there is no default entry. Any RLDX-1 training or serving command for our robot must pass `--modality-config-path`.
- Sim dataset is **26-dim bimanual**; the real dataset (0410) is 20-dim single-hand. Code that handles both must not assume one layout.
- Physics modalities are keyed `observation.{key}` by the loader, so adding torque later means an `observation.torque` column plus `--physics-keys torque`.
- **Only 16 of the 26 action dims carry signal.** Measured from `meta/stats.json` using q99−q01 as a robust spread: `right_arm` 7/7 move (0.70–1.37 rad, the primary manipulator), `right_hand` 5/6 (0.26–0.96, finger flexion; dim 25 pinned at 1.05), `left_arm` 4/7 (0.16–0.46 rad, roughly a third of the right arm's amplitude — postural/supporting), and **`left_hand` 0/6 — every statistic is exactly 0.0000** (dims 14–18 held at 0.0, dim 19 at 1.05).

  Decision: **keep all 26 dims.** The GR00T N1.7 baselines were trained on this same 26-dim space, so reducing it would make a difference in outcome unattributable — which defeats the change's stated deliverable. The eval env's action space is fixed at 26 anyway, so a reduced policy would need constants re-injected at serve time: more adapter complexity and index-error risk for negligible gain. Numerically safe: `state_action_processor.py:155` guards the min/max denominator with `np.maximum(range_vals, 1e-8)`, so zero-range dims normalize to a constant rather than producing NaN.

  **Interpretation caveat for the Phase-1 report:** this "bimanual" dataset is functionally single-arm manipulation with a supporting left arm, and the left hand never actuates. RLDX-1's claimed strength is dexterity-first bimanual manipulation, so this task may not exercise it. If the two models tie, the honest conclusion is "no advantage on a predominantly single-arm task", not "no advantage".

## 5. Serve RLDX-1 into the existing eval harness

**Frame-count decision (2026-08-17): single frame.** The GR00T N1.7 baselines send one frame per step, so RLDX-1 runs `RLDX-1-PT-IMG` at `video_length 1` with video `delta_indices=[0]` to keep the comparison symmetric — and the adapter therefore needs no frame buffer. Upstream's validator is explicit that multi-frame buffering is the *client's* job ("the client must buffer past frames at the action-step offsets shown in delta_indices and send them all in one call, oldest first"), so avoiding it removes a real temporal-alignment risk.

**Consequence to state plainly in the Phase-1 report:** at `video_length 1` the motion module is inert, memory is off (single pick-and-place per episode) and physics is off (no tactile/torque). Phase 1 therefore measures RLDX-1's **Qwen3-VL-8B + MSAT backbone**, not any of its three headline capabilities. A tie means "no advantage on this task with its differentiators unused", not "no advantage".

**Porting `agents/evalbot/harness/` to Pegasus surfaced four real, fixable gaps — none of them Pegasus quirks in the throwaway sense; all four are now fixed at the source in `run_eval.py`/`gr00t_infer_agent.py`, so every future box benefits, including a future 4090 run:**

1. `server_cmd()`/`server_workdir_activate()` had no `"rldx"` branch at all — any RLDX-1 run would have silently tried to launch `gr00t.eval.run_gr00t_server`, the wrong module entirely. Added, matching the flags verified working in 6.5.
2. `main()` called `find_conda_sh()` unconditionally, which raises `SystemExit` if no working conda is found — and Pegasus's `env_isaaclab` conda env has no `bin/activate` and there is no working `conda` binary on the box at all (confirmed: `conda/` there is a package cache only, no binary). Every run would have failed before any of them started. Added `isaaclab_activate()` / `env.isaaclab_conda_prefix`: an explicit env path takes priority over `conda activate NAME`, and `conda_sh` lookup is now lazy (only needed by the non-venv server path, which this run doesn't use).
3. Three Python packages `episode_data_saver.py`/`gr00t.policy.server_client` need — `pandas`, `opencv-python-headless`, `matplotlib`, `msgpack`, `msgpack-numpy`, `pyzmq` — were missing from `env_isaaclab` (this harness had simply never been run through that env before). Installed via pip; `termcolor` was the equivalent gap section 3.1 already found and fixed for IsaacLab itself.
4. **The real find:** `gr00t_infer_agent.py`'s `simulation_app.close()` hangs indefinitely on this box — not only after an unhandled exception (the already-documented Kit-teardown-deadlock pattern), but after a fully successful, clean run too. Every result is already flushed to disk before that call (`finalize_manifest`, `write_manifest`, `simulation_note.txt`, and this process's own unbuffered stdout), so there was nothing to lose by not waiting for it. Fixed: run `close()` in a daemon thread with a 15s join, then `os._exit(0)` unconditionally. Confirmed the difference directly — the pre-fix run finished both episodes (readable straight from the raw client log) but the scheduler's own bookkeeping never advanced past "client attempt 1" because `subprocess.run()` was blocked waiting on the hung process; post-fix, the identical workload completed with `rc=0` and the scheduler's own comparison table populated normally. Without this fix, every successful 100-episode attempt in section 7 would burn the *entire* `client_timeout_s` (14,400s / 4h in the main config) on top of its real runtime, for no reason.

5. **A fifth gap, found the expensive way:** the real 100-episode/3-run launch (2026-08-19) was left running unattended and was checked again 2026-08-21 (after a 2-day gap) expecting it to be done. It was not — `n17_lr5e5_150k_0614` had produced only 11/100 episodes across 11 attempts, each burning the *full* `client_timeout_s` (14,400s / 4h) before being killed. Root cause: `EpisodeDataSaver._save_episode_parquet()` (only reachable when `save_video: true`, which the 2-episode smoke test above had turned *off* — so this never triggered there) calls `pandas.DataFrame.to_parquet()`, and `env_isaaclab` had `pandas` itself but neither of its optional parquet engines (`pyarrow`/`fastparquet`).    Fixed three ways: (a) installed `pyarrow`; (b) wrapped the per-episode `data_saver.save_episode(...)` call in a `try/except` that logs and continues — a save failure must not cost the *remaining* episodes of a long run; (c) wrapped `main()` itself in the `if __name__ == "__main__":` block so *any* future exception there reaches the same fast `os._exit()` path finding 4 already added for the successful case, instead of silently relying on `client_timeout_s` to eventually notice.    **Lesson for the next dependency-gap check on a new box:** verifying an import succeeds is not the same as verifying the code path that uses it works — `import pandas` succeeded the whole time; the actual failure was three calls deep, in a codepath (`save_video: true`) the first smoke test happened not to exercise. Test with the *real* configuration's flags on, not a cheaper stand-in, before trusting a long unattended run to it.

The placement itself looks correct; it just arrives too close to (or just past) the 595-step cutoff.

  Read together, this suggests RLDX-1's failures here are dominated by **hesitation near the final release, not incorrect placement**. Confirmed the exact mechanism by reading the success check itself (`can_sorting/mdp/terminations.py:task_done()`, called directly every step by `gr00t_infer_agent.py:338` — `env_cfg.terminations.success` is set to `None` so the env's own termination manager never fires it; the harness evaluates it standalone and breaks the loop the instant it's `True`): success requires **six conditions simultaneously**, not just "object visually in the basket" — the can's x/y/z position inside the target basket's bounding box, **all three components of the can's velocity under 0.1 (it must have settled, not just arrived)**, **and the right wrist retracted back past `x < 0.10, y < -0.30`** (a specific withdrawn position, not merely "gripper open"). All six must hold at the same step. A frame that looks finished — can resting on the pad, gripper open — still scores `Success: False` for the full 595 steps if the wrist hasn't pulled back far enough yet, or if the can/gripper contact is still imparting a shade of residual velocity above the 0.1 threshold. This is not a settle-window/grace-period issue (there is no such window) — it's a same-step retraction requirement RLDX-1 evidently reaches too slowly in these cases. Neither sampled case showed wandering, oscillation, or picking the wrong object/pad.
