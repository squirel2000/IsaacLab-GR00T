Verdict

Phase 0 passed. Suite mean 97.47% against the 97.4% target (+0.07 pp), all 1100 episodes. Their released checkpoint reproduces their published LIBERO figure on our hardware, so downstream comparisons against it are meaningful. Details in the reproduction section.

Suitable, with one hard limit. Tactile and torque are optional in RLDX-1, not load-bearing — the released LIBERO checkpoint that set their headline number has the physics stream switched off entirely, and the paper's own OpenArm experiments ran without it. So a no-tactile setup like ours loses nothing on the main path.

The hard limit is licensing: the weights are non-commercial with share-alike, so anything we fine-tune inherits that. Fine for the research comparison we agreed; unusable in a product.

The caveat is engineering quality. Their documented LIBERO evaluation does not run out of the box — we hit four distinct defects plus one collision with our own RLinf install before a single episode executed. Treat their benchmark table as vendor-reported until we finish reproducing it.

What RLDX-1 actually is

A correction worth making up front: despite sitting in the same problem space as GR00T, RLDX-1 is not GR00T-derived. It is built on a fine-tuned Qwen3-VL-8B backbone feeding a Multi-Stream Action Transformer (MSAT) — an MMDiT-style block borrowed from FLUX, trained with flow matching, emitting 16-step action chunks.

What it does share with GR00T is the plumbing. RLDX-1 explicitly follows NVIDIA's GR00T N1.7 conventions: EmbodimentTag routing into per-robot MLP encoder/decoder heads, a meta/modality.json that slices flat state vectors into named joint groups, LeRobot datasets, and max_state_dim = 64. That is why our existing dataset layout transfers almost unchanged even though the model lineage is unrelated.

The architectural idea that matters for us is the stream separation. Cognition, action, and physical sensing each get their own token stream, coupled only through joint self-attention — which is precisely what lets the physics stream be removed cleanly.

Do we need tactile and torque?

This was the question that decided whether to look further, and the answer is well-evidenced: no, not for the main path. Four independent lines of evidence agree.

Every check points the same way — physics sensing is an opt-in module bolted on at fine-tune time, not part of the pretrained representation.
EvidenceFindingWeight

The single most convincing item is the first. We inspected the checkpoint that produced their headline LIBERO score, and physics is off in it. The number we are reproducing was never a tactile result.

But we probably do have torque

An incidental discovery worth acting on. OpenArm drives DAMIAO motors over CAN-FD, and enactic/openarm_can's Motor class already exposes get_torque() (backed by state_tau_) alongside position and velocity. The joints are QDD-backdrivable with bilateral force feedback for teleoperation, so that signal is real.

That is exactly the modality ALLEX uses — joint torque, no force/torque sensor — and it matches the report's "up to 7-dimensional torque signals". We simply aren't logging it. Both can-sorting datasets record 20-dim state and nothing else. Adding a 14-dim observation.torque field would unlock --use-physics --physics-keys torque whenever we want it.

The weak link is the hand, not the arm. The LinkerHand O6 is worm-gear driven and therefore non-backdrivable, so its torque reading reflects motor effort rather than contact force. Its genuine tactile call, get_force(), is documented for the L7/L10/L20/L25 — on the O6, fingertip tactile is an optional add-on worth confirming with the vendor.

RLDX-1 reports gains over GR00T N1.6 across every published suite. Two things to keep in mind while reading: there is no GR00T N1.7 comparison anywhere — our actual baseline is unmeasured against it — and the repo's own README quotes lower figures than the paper.

Phase 0

Reproducing it ourselves

Before spending any training budget we gated on a single question: can we reproduce their published LIBERO number using their released checkpoint and their own code? If not, no downstream comparison would mean anything.

The evaluation is a two-process, two-environment affair, and that split is where most of the trouble lives. The 6.9B model runs as a ZeroMQ server in the main uv venv on torch 2.7. The rollout workers run in a separate venv on torch 2.5.1, because LIBERO and robosuite need an older, conflicting stack — yet those workers still import rldx, so they need the model dependencies too.

Five things we had to fix

These are ordered as encountered — each one hid the next, so they could only be found serially. Upstream's setup_libero.sh reports success throughout, because its own verification step is non-fatal.

1

Missing diffusers

setup_libero.sh installs the rldx package with --no-deps and never adds diffusers, which action_model/attention.py imports at module scope. The rollout client imports rldx.data.embodiment_tags, and rldx/__init__.py:66 eagerly pulls in the entire model stack.

ModuleNotFoundError: No module named 'diffusers'
2

Their own transformers pin is too old for their own code

The setup script pins transformers==4.51.3, but modeling_qwen3_vl.py imports transformers.masking_utils.create_causal_mask, which only exists from 4.52. Aligned to 4.57.0 to match the model server.

ModuleNotFoundError: No module named 'transformers.masking_utils'
3

Unpinned mujoco drifted past robosuite's API

LIBERO pins robosuite==1.4.0; robosuite declares only mujoco>=2.3.0 with no ceiling, so the resolver took 3.11.0. Newer MuJoCo renamed the mass matrix — MjData.qM is gone, replaced by M/qLD/qLDiagInv — while robosuite's OSC controller still calls mj_fullM(..., sim.data.qM). We found the working ceiling empirically against the real reset test rather than guessing: mujoco 3.2.7.

AttributeError: 'MjData' object has no attribute 'qM'
4

Readiness probe assumes a tool this host doesn't have

eval_libero.sh waits for the server by grepping ss -lnt. Pegasus ships neither iproute2 nor net-tools, so the probe never matches: their script waits 120s and exits 1, even though the server is up and listening. We verified via /proc/net/tcp that the port was in state 0A the whole time, and replaced the probe with a direct kernel-table read.

[!] Server died before binding to :PORT # it hadn't
5

Collision with our own RLinf install not upstream's fault

LIBERO caches absolute asset paths in a per-user ~/.libero/config.yaml. Ours was written in June by the RLinf N1.7 work and pointed at /data/VLA/tingying/RLinf/.venv/libero/..., a tree that no longer exists — so every task died looking for its .bddl. Upstream preserves this file unless FORCE_CLEAN=1, which is defensible but bit us. Fixed non-destructively with LIBERO_CONFIG_PATH pointing at an isolated config, leaving the shared one intact for RLinf.

AssertionError: .../libero_goal/turn_on_the_stove.bddl does not exist!

Taken together these corroborate the two open reproducibility issues upstream (#24, where GR1 Tabletop reproduces at 55.75% against a reported 58.7%, and #25). None of the five is deep — but a benchmark suite that cannot execute unmodified is a benchmark suite nobody has re-run.

Reproduction: passed

With the environment repaired, the sweep ran under a resumable supervisor: per-task completion markers, automatic server restart, and up to three retry passes, so an interruption re-runs only what didn't finish. It completed all 40 tasks in one pass on a single H100 — zero task failures, zero server restarts.

Two measurement traps worth recording

Getting a trustworthy number turned out to be harder than getting a number, and both traps would silently bias anyone else's reproduction.

Don't count video files. The obvious tally — globbing *success*.mp4 — is wrong twice over. Episodes that hit the 720-step cap without finishing are skipped for video recording entirely (148 of our 1100), so they vanish from the denominator. And rollout_policy.py targets int(n_episodes/n_envs) per env but only breaks once every env reaches that target, so faster envs overshoot and write extra videos — we saw 68 files for a 50-episode target. Filename counting gave 94.06% where the real figure was 95.45% on the same partial data: a 1.4 pp error, which against a 97.4 threshold is decision-changing. simulation_results.csv is the real record — one row per (env_idx, episode_idx) with an explicit int(success).

Don't episode-weight the average. LIBERO is conventionally reported as the mean over its four suites, each equally weighted. But libero_10 runs 50 episodes per task against 20 for the others, so it takes 500 of 1100 episodes — 45% — and it is the hardest suite. Episode-weighting our own final data gives 96.64%, which would have read as a MISS. The suite mean is 97.47%, a PASS. Same episodes, same successes, different arithmetic.

Independent cross-check. rollout_policy.py prints its own per-task success rate on completion; averaging those 40 values is a completely separate derivation from our CSV tally, and it agrees to 0.01 pp.

Stereo is not a requirement. "Stereo egocentric cameras" in the paper describes the ALLEX and OpenArm hardware, not a model constraint. There is no disparity or depth machinery anywhere in the architecture; cameras are independent video.<key> entries and nothing pairs them. Their FR3 experiments used wrist plus third-person — the same topology as our head plus wrist — and the LIBERO result we're reproducing uses monocular agentview plus eye-in-hand. A PT-IMG checkpoint even exists for single-frame, single-view use.

Our own datasets, however, contain only one camera stream despite the robot carrying two. Re-exporting with both is the highest-value cheap change available, and it is not RLDX-specific.

On compute: the model occupies 15.1 GB in bf16, so inference fits comfortably on one H100 and would fit a 24 GB RTX 4090 — usefully, the 4090 is sm_89 and takes the standard prebuilt flash-attn wheels, avoiding the source build that sm_120 requires. Full fine-tuning of 6.9B with AdamW needs roughly 110 GB of weights, gradients and optimiser state, so on two H100s LoRA is the realistic path, which is also what "just confirm the result" calls for.

Shortcomings

  1. Non-commercial weights, share-alike. RLWRLD Model License v1.0 §3.1 limits use to research, education, personal or evaluation purposes; §3.5 bars military use. Derivatives inherit the terms, so a fine-tuned OpenArm checkpoint could never ship. Apache-2.0 on the code does not rescue this. This is the decisive constraint.
  2. Reproducibility unverified by anyone else. Two open issues report gaps; a third asks for external verification and is still open.
  3. No GR00T N1.7 comparison exists. Our real baseline has never been measured against it.
  4. 2–2.3× the parameters of GR00T N1.5 for every train and inference cycle, permanently.
  5. Undocumented requirements. No VRAM figures, no minimum dataset size, and the paper omits demonstrations-per-task for the real-robot runs.
  6. The parts carrying much of the gain aren't released. Synthetic data lifts tabletop from 41.0% to 50.1% and RL refinement gives roughly 3× fewer attempts, but neither the generation pipeline nor the RL code ships — the repo is fine-tune and serve only.
  7. Stateful serving. The memory module needs reset_memory at episode boundaries and stable session IDs; our eval harness and RL rollout loop both need changes to stay correct.
  8. Single-camera data underuses the architecture — video token compression, 4-frame input and the motion module all assume richer views.
  9. Young project. Created 27 Apr 2026, last push 3 Aug 2026; 10 open issues, mostly Dependabot, plus contributor friction.
  10. Ecosystem cost. Adopting it means maintaining a second VLA lineage — different backbone, trainer and serving stack — beside GR00T.

Where this goes

A bounded research comparison, not a stack migration.

  1. Phase 0 — reproduce LIBERO. passed 97.47% suite mean vs 97.4% target. The gate is cleared, so Phase 1 is authorised.
  2. Phase 1 — LoRA on sim can-sorting (2000 episodes, physics off) head-to-head against GR00T N1.7 on identical data and metrics.
  3. Phase 2 — does the memory module earn its keep? An A/B on multi-task can-sorting. This needs no new sensing and GR00T has no equivalent, which makes it the highest-information experiment available.
  4. Phase 3 — small and deformable objects from real collection, since these can't be built in sim. This is where contact-force feedback should start to matter and where logging OpenArm's torque gets reconsidered.

Regardless of whether we adopt the model, two ideas are worth harvesting into our existing stack: Real-Time Chunking for smooth action-chunk boundaries, and their text-based-critic RL refinement — directly relevant to the RLinf N1.7 work, where scale rather than critic design turned out to be the bottleneck.
