三個核心結論:
  1. N1.7 不是結構性比較差。同一個 backbone 換 recipe(較低 LR、更長訓練)後達到 98%,反超 N1.6 的 94%,且完成任務更省步。
  2. Train loss 與閉迴路成功率脫鉤。N1.7-300k 的 loss(0.0071)仍是 N1.6(0.0028)的 約 2.5 倍,成功率卻更高——train loss 是「發散哨兵」,不是任務表現的量尺。
  3. 評測環境必須對齊訓練資料分布。multitask 任務若餵固定語言 prompt,所有模型的 成功率都會被系統性壓低、且程度不一,足以顛倒排名。

2. 專案目標與範圍

出發點:在相同 recipe(150k steps、LR 1e-4、no_tune_llm / no_tune_visual / tune_projector / tune_diffusion、state_dropout 0.2、global batch 32)下, N1.7 的 train loss 收不到 N1.6 的水準。要回答的問題是: 這個差距是「訓練不足(recipe 問題)」還是「新 backbone 的結構性缺陷」? 以及 train loss 到底能不能代表任務表現?

兩版模型的架構差異(讀取 checkpoint config.json 確認):VLM backbone 從 Eagle-Block2A-2B-v2 換成 Cosmos-Reason2-2B(Qwen3VL);DiT action head 完全相同 (32 層、32 heads、head_dim 48、output 1024);N1.7 新增 4 層 VL self-attention; action_horizon 50→40;max action/state dim 128→132。

專案分三條工作線:

  1. 訓練側評測基礎設施:hold-out(held-out)資料集切分、訓練中 open-loop eval callback、最佳 checkpoint 保存、early stopping。
  2. 閉迴路評測:IsaacSim 內實跑 policy 算成功率,crash-resilient orchestrator, 三個 checkpoint × 100 episodes ×(視窗 + headless)。
  3. 專案結構整理:評測 harness 集中到父 repo scripts/eval/(單一入口 run_eval.py), IsaacLab submodule 瘦身到對 develop 幾乎零差異。

3.3 Crash-resilient 迴圈(為什麼能無人值守過夜)

IsaacSim client 會間歇性死於 Omniverse PhysX 重入 bug (carb.tasking Mutex Recursion not allowed,發生在 episode reset)。對策:

▼
server 還活著?(kill -0)— 死了就重啟並重新 wait_ready
▼

▼

統計與比較:run_eval.py 跑完自動解析各 run 的 combined log,印出 success/timeout/unsafe 並輸出 success-vs-loss 比較圖。

3.4 訓練側:三層評測訊號與訓練中評測流程

訊號量什麼成本用途與限制
① train lossflow-matching velocity MSE,訓練資料上免費 發散/崩壞哨兵。不是任務表現的代理(本專案的鐵證)
② held-out open-loop action MSE未參與訓練的 episodes 上,完整去噪後的動作誤差低 泛化訊號:選最佳 checkpoint、抓 overfitting 起點、驅動 early stopping;但仍是 open-loop
③ closed-loop success rateIsaacSim 實跑任務成功率高(數小時) 最終真理;留給關鍵決策

hold-out dataset:從同一份 LeRobot dataset 依 episode 切出訓練不碰的子集 (以 episode 為單位、不是以 frame,否則相鄰 frame 高度相關會洩漏)。 為此在 Isaac-GR00T_n1d7 加了訓練中評測(方案 B,in-loop callback):

dataset 依 episode indices 切 train / val(in-memory split,啟動時驗證兩邊皆非空)
▼ 每 eval_steps
eval 迴圈:對 val batch 以固定 seed 的 noise/timestep(common random numbers) 算 eval_action_mse(+ 各關節分項)——曲線只反映模型變化,不含 RNG 抖動
▼
依 metric 保存 best checkpoint(checkpoint-*-best-eval_action_mse_*); 可選 early stopping(patience / min_delta,預設關閉);多 GPU 情境 fail-loud 防 gather 死鎖
這個 held-out MSE 在訓練過程中由上述 callback 即時計算;訓練後要回看, 讀各 checkpoint 的 trainer_state.json 即可(見 §5 圖表)。

4. 問題與結論(Q&A 總整理)

Q1.「N1.7 大幅落後」的第一輪結果,為什麼是假象?怎麼修?

第一輪評測對所有 episode 餵同一句固定的語言描述。但 dataset 0403 是 multitask:語言標註隨目標顏色而變(橘盤/綠盤兩種指令)。固定 prompt 等於約一半的 episode 收到與目標不符的指令——所有模型成功率被系統性壓低、且受影響程度不一, 導致第一輪數字(已作廢)嚴重失真、甚至顛倒了對 N1.7 的判斷。

修正(三處,參考 commit 2069bbdd 但描述字串以 dataset meta/tasks.jsonl 為準):

  • can_sorting/mdp/observations.py:新增 target_object_color_obs() 把目標顏色 id 暴露成 observation;
  • can_sorting_env_cfg.py:SceneObsCfg 加對應 ObsTerm;
  • gr00t_infer_agent.py:每步依 color id 切換 task description; 並把 --pov_list 改為 head-only(dataset 只有一台相機,三相機不對齊訓練分布)。

誠實但書:修正同時動了「prompt 切換」與「相機數」兩件事;但切相機前以 3 相機 + multitask prompt 試跑 4 集得 4/4,顯示 prompt 是主因。

Q2. train loss 幾乎一樣(0.0078 → 0.0071),成功率卻 75% → 98%。不是質變嗎?

不需要「質變」,這是模仿學習(behavioral cloning)的標準現象,兩個機制:

  • Covariate shift / 誤差累積:train loss 量的是「訓練資料分布」上的誤差; 閉迴路 rollout 時 policy 自己走,state 逐步偏離訓練分布。兩個模型在訓練分布上 誤差相同,在「偏離後的 state」上可以差很多;595 步的 horizon 把每步小差異滾成 「能不能完成」的差別。
  • 平均 loss 被簡單樣本主導:任務成敗卡在少數 bottleneck state(抓取、對位那幾步), 它們對「對所有 (state, noise, timestep) 取平均」的 loss 幾乎沒貢獻。模型可以在關鍵 state 上變好(成功率上升)而平均 loss 不動。
Q3. 那 train loss 還能拿來當訓練依據嗎?

Necessary but not sufficient(必要但不充分)。本專案把這點推到極致: N1.7-300k 的 train loss 比 N1.6 差約 2.5 倍,閉迴路成功率卻更高(98% > 94%)。

  • loss 爆掉一定有問題(發散哨兵),但 loss 漂亮不代表任務會成功;
  • 正確的訊號層級:train loss → held-out open-loop MSE → closed-loop success(見 §3.4);
  • 這正是建 held-out eval + early stopping 基礎設施的理由:只看 train loss 會被誤導。
Q4. 75% → 98% 的改善,可以歸因於「LR 減半 + steps 加倍」嗎?

不能乾淨歸因。逐項比對兩個 run 的設定後,已控制的變數:base model、dataset、 modality、state_dropout、batch、freeze 設定全部相同;但混淆變數有:

變數N1.7-150kN1.7-300k
learning rate1e-45e-5
max steps / warmup150k / 0.05300k / 0.10
code repo(相差約一個月的大改版)Isaac-GR00TIsaac-GR00T_n1d7
shard / sampling 參數預設明確指定

所以誠實的結論只能是:「新 recipe + 新 code 整體把 N1.7 推到 98%,且是在 train-loss 差距沒有縮小的情況下達成」。要單因子歸因,需補一個 controlled run (用新 code 重跑 LR 1e-4 / 150k)——目前沒有。

Q5.「誤差沿 horizon 累積」有理論根據嗎?

有,但要分清楚哪部分有根據。

  • 有根據:behavioral cloning 的 covariate shift 是經典結果——Ross & Bagnell (AISTATS 2011,DAgger 論文)證明純 BC 的 worst-case regret 隨 horizon 成長約 O(T²·ε)(DAgger 改善為 O(T·ε))。這直接支撐 Q2 的「小誤差沿 595 步放大」。
  • 沒有根據(只是假說):「較低 LR + 更長訓練讓 flow-matching 的 velocity field 更平滑、ODE 積分更穩」——無具體文獻支持,且與 Q4 的混淆變數糾纏,當 hypothesis 看待。
Q6. backbone 從 Eagle 換成 Cosmos/Qwen3VL(DiT 不變),最終判決是什麼?
  • 不是結構性缺陷:同一個 N1.7 backbone 換 recipe/code 後達到 98%,反超 N1.6。
  • 但 N1.7 的 train-loss floor 結構性偏高(150k:2.8×;300k 仍 2.5× N1.6), retrain 沒有改變這點——很可能源自不同 VLM/normalization;
  • 而這個 loss 差距與閉迴路表現完全脫鉤(loss 較差的模型任務表現較好)。 工程結論:N1.7 可用且優於 N1.6,不要拿 train loss 跨版本比較。
Q7. 沒有螢幕的 H100 可以跑閉迴路評測嗎?(headless 驗證)

可以。以 headless 模式且完全無 X display 重跑三個 checkpoint × 100 eps, 與視窗(:0)基準比較:94→98、75→78、98→95(總計 267/300 → 271/300)。 所有差異都在 binomial 抽樣噪音內,且成功 episode 的步數分布高度重疊 (渲染觀測等價的最強證據)。關鍵:agent 強制 enable_cameras=True, headless 下相機仍離屏渲染。→ 成功率評測與參數調校可直接搬上無螢幕的 H100, 用 HEADLESS=1 開關。

Q8. 評測數字的統計可信度?

每個 checkpoint 100 episodes 的 binomial 標準誤 ≈ √(p(1−p)/100):p≈0.9 時約 ±3%、 p≈0.75 時約 ±4.3%。因此 94 / 75 / 98 之間的差距遠超噪音;而視窗 vs headless 的 ±3~4 點差異則在噪音內。失敗型態也一致:幾乎全是 timeout(595 步內未完成), 0 例不安全終止——模型「慢」而不「危險」。

Q9. 專案結構(submodule)怎麼收斂?(Q3 清理)

原則(使用者定):IsaacLab submodule merge 回 develop 時差異量要最少; 不在 develop 上的東西盡量不要留在 IsaacLab 內。做法見 §6。

7. 本專案的收獲

  1. 評測 harness 本身要先被驗證。結論被「測試環境的一個 prompt 設定」翻轉過一次—— 在相信任何模型比較前,先確認評測輸入(語言、相機、modality)與訓練資料分布一致。
  2. Train loss 只能當哨兵。跨 backbone 比 loss 沒有意義;訓練決策要靠 held-out open-loop MSE,最終判決靠 closed-loop success。
  3. 模仿學習的成敗在 rollout 分布,不在訓練分布。O(T²ε) 的誤差累積讓 「平均誤差相同」的兩個模型在長 horizon 任務上表現迥異。
  4. 下結論前先列混淆變數。150k→300k 同時換了 code repo,所以只能下 「整體 recipe 有效」的結論,不能歸因單一因子;需要 controlled run 才能切開。
  5. 100 episodes 的噪音是 ±3~4%。個位數百分點的差異不要解讀; 失敗型態(timeout vs unsafe)比單一數字更有資訊量。
  6. 無人值守的評測需要 crash-resilient 設計。server 常駐 + client 重啟補跑 + 以逐 episode log 為事實來源,讓 PhysX 隨機崩潰不再毀掉整晚的 run。
  7. Headless 渲染與視窗等價(本任務、RTX 4090 驗證)→ 評測可遷移到無螢幕的 H100。
  8. 訓練中評測要控制隨機性。flow-matching 的 eval 若每次抽新 noise/timestep, 曲線的抖動來自 RNG 而非模型;固定 per-batch seed(common random numbers)才能看趨勢。
  9. Submodule 衛生:fork 專用工具放父 repo,submodule 對上游保持最小 diff, merge 才不痛。
