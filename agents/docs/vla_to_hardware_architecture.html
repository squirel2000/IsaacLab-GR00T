🏗️ System Overview

A GR00T vision-language-action policy emits 16-step action chunks at a 30 Hz dispatch cadence. Each chunk is sent as a single FollowJointTrajectory goal; the ROS2 JointTrajectoryController (JTC) interpolates between waypoints and writes a position command, which the hardware component's 500 Hz MIT-control loop tracks on the Damiao motors.

Core finding. The pipeline spans six update rates (30, 60, 100, 200, 500 Hz). Before optimization the 100 Hz controller_manager was the bottleneck: it throttled JTC interpolation and, because the motor loop runs at 500 Hz, every command was repeated 5× (a staircase). Raising the manager to 500 Hz and adding finite-difference velocity hints (linear → cubic interpolation) removed the staircase and the velocity discontinuities. The wins are in timing regularity and command smoothness — not in gross tracking of slow VLA-paced motion, which looks the same either way.

🔀 State Streams & Rates

/joint_states, /<ctrl>/controller_state, state_publish_rate, update_rate and control_hz are easy to conflate. Two different topics carry "state," produced at different rates for different consumers:

NameRate (now)WherePurpose
update_rate500 Hzcontroller_manager (C++)How often the JTC interpolates and read()/write() run.
/joint_states500 Hzjoint_state_broadcasterActual feedback for everyone (RViz, VLA, bag), sourced from the motors via state_read_loop.
/<ctrl>/controller_state100 Hzeach JTCReference vs feedback vs error — diagnostics / analyzer only; the VLA node never subscribes.
joint-state spin200 Hzgr00t_control_robot.pyIdle-wait bound that keeps self.joint_state fresh; consumes /joint_states.
control_hz30 Hzcontrol_loop()VLA action-chunk dispatch cadence (= JTC waypoint spacing).
Key points
  • /joint_states is the only state the Python node consumes; controller_state feeds only the offline analyzer.
  • The 200 Hz spin is an idle-wait bound: with /joint_states at 500 Hz the loop drains messages as they arrive and keeps the newest; the control loop only uses the state at 30 Hz (at inference).
  • STATE_FILTER_CUTOFF_HZ (50→100) does not touch the motor firmware PD (raw on-board encoder); it only affects the gravity/friction feed-forward and the observed/published state.

🔄 JTC Interpolation Behavior

The JTC interpolation method depends on which fields each trajectory point carries:

Fields providedInterpolationContinuity
Position onlyLinear (straight line between points)C0 — position continuous, velocity discontinuous
Position + VelocityCubic splineC1 — velocity continuous
Position + Velocity + AccelerationQuintic splineC2 — acceleration continuous

A chunk packs 16 waypoints (33 ms apart, 533 ms total) into one goal. A new chunk arrives roughly every inference cycle and preempts the previous trajectory, so only the first ~1–3 waypoints of each chunk actually execute. With position-only points the per-segment velocity is a staircase (jerk spikes at every waypoint); the Phase 2 finite-difference velocity hint promotes this to a cubic spline, and the hint at the first point preserves velocity continuity across the preemption.

Why cubic, not quintic? Quintic (C2) needs second-order finite differences over three positions; VLA action chunks are noisy and second derivatives amplify that noise. Cubic (velocity only) is the best smoothness-to-robustness trade-off — confirmed by the ~24× drop in commanded-acceleration spikes without introducing high-frequency chatter.

🧵 Hardware Thread Architecture

The launch (openarm_o6_bimanual_lpf.launch.py) loads two hardware instances (left + right arm), each running the OpenArm_v10LPF_HW plugin. Threads per system:

Not launched: leap_control_loop() (config uses O6, not LEAP). The standalone LeapHandHardware / O6HandHardware plugins are registered but not loaded — the arm plugin handles the hand internally. The LPF variant overrides write() to add a command-side LPF (default 10 Hz) in addition to the state-side LPF.

⚠️ Rate-Mismatch Issues — Addressed

SE-1: JTC command rate ≠ motor write rate — resolved

At 100 Hz the 500 Hz motor loop saw the same command 5× (a staircase; measured ~78 Hz effective setpoint changes). Raising update_rate to 500 Hz makes the JTC write every motor cycle (~395 Hz measured setpoint changes).

SE-2: Linear interpolation from position-only points — resolved

Without velocity hints the velocity profile jumped at every 33 ms waypoint. Phase 2 adds finite-difference velocities → cubic spline; commanded-acceleration p99 dropped ~24× (278→11 rad/s²).

SE-3: VLA observed stale joint states — resolved

The 30 Hz spin missed most of the 100 Hz publishes. The spin is now 200 Hz and /joint_states is 500 Hz, so self.joint_state is fresh to within a few ms.

SE-4: vel_cmd = 0 in MIT feed-forward — deferred

The JTC writes only the position command interface, so the motor's velocity feed-forward term is always 0. Adding it (a command_interfaces: [position, velocity] experiment) is low-value for slow VLA motion with low kd, and risks injecting noisy finite-difference velocity — deferred by choice.

Latency riskHigh (OS file-I/O stalls)Zero
Data completenessEvery 100th sampleEvery sample (last 120 s)
Implemented (Phase 3): each arm_control_loop iteration writes one snapshot into a pre-allocated ring buffer (debug_ring_) at 500 Hz with zero file I/O; the CSV is written once in flush_debug_ring_to_csv() from on_deactivate() after the arm thread is joined. Column format is unchanged, so analyze_vla_pipeline.py --csv works as-is.
Operational limits:
  • It is a ring buffer holding only the most recent DEBUG_RING_SECONDS (default 120 s ≈ 31 MB/arm); a longer session keeps only the last 120 s.
  • The CSV is written only on a clean on_deactivate(). A kill -9, crash, or power loss writes nothing — confirm the "Flushed N debug samples…" log on stop.
  • For longer captures raise DEBUG_RING_SECONDS in v10_simple_hardware.hpp (memory scales linearly) and rebuild. A crash-proof / unbounded logger would need a dedicated background flush thread (deferred).

📐 State LPF After the Rate Increase

Raising CONTROL_READ_RATE_HZ 200→500 changes the LPF behaviour at a fixed cutoff, so STATE_FILTER_CUTOFF_HZ was raised 50→100 Hz to keep the filter responsive.

α = Δt / (RC + Δt)  where  RC = 1 / (2π·fcutoff) , Δt = 1 / fsample
SampleCutoffαEffect
200 Hz (old)50 Hz0.61Mild filtering at the old rate
500 Hz50 Hz0.39Same cutoff, now noticeably sluggish
500 Hz100 Hz0.56Applied — responsive, ~17° phase lag at 30 Hz
500 Hz150 Hz0.65Near-transparent (almost raw)
At 500 Hz, Nyquist is 250 Hz; VLA content is ≤30 Hz, so a 100 Hz cutoff rejects high-frequency noise while preserving the useful band. The command-side LPF in v10_lpf_hardware still defaults to 10 Hz (α≈0.11 at 500 Hz — heavy); it is a launch argument (cmd_filter_cutoff_hz), so try :=15 or :=20 without rebuilding if command lag is felt.

🔁 Reproduce the Analysis

All analysis lives in Isaac-GR00T/scripts/analysis/. Run it with the env_gr00t conda python (numpy/pandas/matplotlib/scipy/rosbags) — the system python lacks the stack.

1 · Record a session

Press L in gr00t_control_robot.py: the recording toggle now also spawns record_vla_session.py as a subprocess (own process group) and stops it with a clean SIGINT so the bag is finalized. The 500 Hz motor CSV is written separately by the hardware component on controller deactivate. Or run the recorder by hand:

python3 scripts/analysis/record_vla_session.py --prefix baseline   # Ctrl-C to stop

2 · Analyze one session

python3 scripts/analysis/analyze_vla_pipeline.py \
  --bag <session>/gr00t_*  --csv <session>/debug_right_*.csv \
  --out <session>/analysis

Latency dashboard, per-joint tracking (actual = red, JTC reference = blue, error = green, in rad), velocity continuity, and motor-level CSV plots. The arm joint count is data-driven, not hardcoded.

3 · Compare two sessions (the figures above)

python3 scripts/analysis/compare_vla_sessions.py \
  --a artifacts/outputs/vla_record_original --a-label "baseline (100Hz)" \
  --b artifacts/outputs/vla_record_p3       --b-label "phase0-3 (500Hz)" \
  --out artifacts/outputs/comparison

Writes session_comparison.png (Figure 1) and command_chain_comparison.png (Figure 2) plus a printed metrics table. Rate/jitter/command-shape metrics compare cleanly across motions; for a strict tracking-accuracy A/B, record the same scripted trajectory under both configs.
