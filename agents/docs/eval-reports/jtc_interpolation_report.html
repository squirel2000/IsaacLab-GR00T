TL;DR — Yes, you are right. Because gr00t_control_robot.py publishes JointTrajectoryPoint.positions only (no velocities, no accelerations), and the JTC is configured with a position-only command_interfaces, the JTC’s splines interpolator degenerates to linear interpolation between the 30 Hz waypoints when stepping at the 100 Hz controller update rate. 2. JTC Interpolation Rules (ros2_controllers)

The joint_trajectory_controller’s spline interpolator inspects each JointTrajectoryPoint and selects the highest-order polynomial it can fit from the data actually present:

Data in JointTrajectoryPointEffective interpolationBoundary continuity
positions only Linear (1st-order) Position C⁰ · Velocity discontinuous (step) at waypoints
positions + velocities Cubic Hermite spline (3rd-order) C¹ continuous · Acceleration discontinuous
positions + velocities + accelerations Quintic spline (5th-order) C² continuous · Jerk discontinuous
interpolation_method: none Zero-order hold (sample-and-hold) Step waveform — usually undesirable
Important nuance: setting interpolation_method: splines does not magically produce a cubic curve from positions alone — the spline coefficients literally require the velocity (and optionally acceleration) values at the knots. With only positions supplied, the spline reduces algebraically to the linear case. Cubic / quintic behavior is unlocked by the data you publish, not by the parameter alone.

Figure 3. Velocity is the derivative of Figure 2. Linear interpolation gives a staircase velocity that jumps at every 30 Hz waypoint — this is felt by the hardware as impulsive torque commands. Cubic/quintic profiles keep velocity continuous (and quintic keeps acceleration continuous too).

4. Why This Matters for the OpenArm

  • jerk Each waypoint boundary is a velocity step → infinite (theoretical) jerk → controller PID and HW current loops respond with a torque spike. On a 7-DoF compliant arm this manifests as audible clunks and small overshoot at every ~33 ms.
  • tracking error Real motors cannot follow a step in velocity, so the position trace lags the reference inside each segment; lag is then "caught up" abruptly at the next knot, producing the same micro-overshoot.
  • audible / vibratory artifacts A 30 Hz waypoint cadence puts the discontinuity rate squarely in the structural-resonance band of most light arms (and well inside human hearing) — even when amplitudes are small, the excitation is broadband.
  • stale-chunk transitions Every new GR00T inference replaces the queue, so the very first interpolated step of a new chunk is linearly interpolated from the current hold target to the first new waypoint — a second category of velocity step on top of the per-knot ones.
  • no feed-forward velocity Because command_interfaces is position-only, even if you supplied velocities in the message JTC would only use them for interpolation shape, not for HW feed-forward. That removes one of the cheapest sources of tracking improvement.

5. Recommendations to Improve Control Performance

Ordered from cheapest / smallest blast radius to most invasive.

R1 · Publish finite-difference velocities with each point low effort, high payoff

Compute velocities from your already-known chunk positions and timing — JTC will then run a cubic Hermite interpolation instead of linear. C¹ continuity removes the per-waypoint velocity step entirely. 

# in send_joint_trajectory(), after building positions_seq
import numpy as np
P  = np.asarray(positions_seq)                     # (N, dof)
dt = 1.0 / control_hz
# central differences with one-sided ends; clamp end velocity to 0
V = np.zeros_like(P)
V[1:-1] = (P[2:] - P[:-2]) / (2.0 * dt)
V[0]    = (P[1] - P[0]) / dt
V[-1]   = 0.0                                       # safe terminal velocity

for i, (pos, vel) in enumerate(zip(P, V)):
    point = JointTrajectoryPoint()
    point.positions  = pos.tolist()
    point.velocities = vel.tolist()                 # <-- unlocks cubic
    t = (i + 1) * dt + delay
    point.time_from_start.sec     = int(t)
    point.time_from_start.nanosec = int((t % 1.0) * 1e9)
    goal_msg.trajectory.points.append(point)
Heads-up: your config still has allow_nonzero_velocity_at_trajectory_end at its default (true on Humble), so you don’t need to force the last velocity to zero — but doing so on the final chunk of a motion avoids overshoot.

R2 · Also publish accelerations (quintic) incremental

A second pass of finite differences on V gives accelerations. With both vel + acc, JTC uses a quintic spline (C² continuous). This is the smoothest profile JTC offers and costs almost nothing if you’re already computing velocities.

R3 · Pre-densify the chunk on the Python side orthogonal & safe

Resample your 16-point, 30 Hz chunk to e.g. 100 Hz using scipy.interpolate (CubicSpline or Akima1DInterpolator — Akima is great for reducing overshoot when waypoints have noise) and send the denser trajectory. Even with positions-only, the JTC then linearly interpolates between samples spaced at exactly the controller period — the linearization error collapses, and you also get full visibility/control over the smoothing in Python (easier to tune than tweaking JTC params). 

from scipy.interpolate import CubicSpline
ts = np.arange(len(P)) / control_hz                     # 0, 1/30, 2/30, ...
cs = CubicSpline(ts, P, axis=0, bc_type="clamped")      # clamped: zero vel at ends
ts_dense = np.arange(ts[0], ts[-1] + 1e-9, 1/100.0)     # match update_rate
P_dense  = cs(ts_dense)
V_dense  = cs(ts_dense, 1)                              # also publish vel for safety

R4 · Apply a temporal low-pass on the policy output use with care

GR00T action chunks can be jittery between predictions. A short EMA on the executed sample, e.g. θ_cmd ← α·θ_chunk + (1−α)·θ_cmd_prev with α ≈ 0.3–0.5 at 100 Hz, dramatically reduces high-frequency content but adds latency proportional to 1/α — tune against the manipulation task closed-loop, not in isolation.

R5 · Overlap / blend consecutive chunks instead of hard replacement structural change

Today, the script accepts a new chunk and the JTC discards the rest of the previous one. At the cutover, the spline restart point is “current state → new chunk[0]”, which re-introduces a velocity step. Two mitigations:

  • Drop the first k samples of the new chunk so its starting state matches where the arm already is (your code already does cutoff_step; verify k is chosen so the velocity matches, not just position).
  • Use receding-horizon blending: cross-fade between the tail of the old chunk and the head of the new one over a window of ~30–50 ms. Cheap, and removes the cutover transient entirely.

R6 · Add a position + velocity command interface (and an FF-velocity gain) requires HW driver change

Switching command_interfaces to [position, velocity] lets the JTC send both the interpolated reference and its derivative to the hardware. Combined with gains.<joint>.ff_velocity_scale > 0 this routes a velocity feed-forward through the JTC’s internal PID, cutting position lag substantially with no extra latency. This requires the OpenArm ros2_control hardware interface to expose velocity as a writable command. Worth checking before relying on it.

R7 · Match the policy update to the arm bandwidth model / dataset work

30 Hz waypoints + 16-step chunk = ~530 ms horizon. For contact-rich manipulation the bandwidth bottleneck is the waypoint cadence, not the controller. If feasible (depends on how you trained the policy), raise control_hz to 50–60 Hz so the controller interpolates over ≤20 ms segments. With dense waypoints, even plain linear interpolation becomes visually smooth, although it’s still worth doing R1 to remove the velocity discontinuities.

R8 · Raise the controller_manager update_rate verify CPU / RT budget

Going from 100 Hz to 200–500 Hz reduces the per-sample staircase amplitude (because Δθ per controller step shrinks). It does not remove the velocity discontinuity, but it pushes the spectral content of the artifact upward (further above the arm’s mechanical bandwidth) and lets the inner current/velocity loops smear it out. Pair with R1 for best effect.

6. Suggested Combination

Pragmatic plan (1 PR, no driver changes):
  1. R1: finite-difference velocities → cubic Hermite at the controller.
  2. R3: pre-densify with a CubicSpline to ~100 Hz, send positions + velocities.
  3. R5 (partial): pick cutoff_step to match velocity, not just position, at chunk handover.
This is a self-contained change inside gr00t_control_robot.py and should remove the per-knot clunks immediately on the existing hardware stack.

7. How to Verify

  • ros2 topic echo /left_joint_trajectory_controller/controller_state — check desired.velocities trace for the staircase (before) vs ramp (after).
  • ros2 topic hz /joint_states — confirm 100 Hz feedback aligns with command updates.
  • Plot actual.positions minus desired.positions from /controller_state: per-knot error spikes should disappear.
  • Bag joint_states + controller_state across a 5 s motion for an identical task before/after — compare FFT of joint velocities; the 30 Hz spike (and its harmonics) should drop with R1+R3.

Refs: ros2_controllers joint_trajectory_controller (Humble) interpolation parameters (interpolation_method ∈ {splines, none}, default splines); the spline order is chosen by which of positions/velocities/accelerations are populated in each JointTrajectoryPoint.
