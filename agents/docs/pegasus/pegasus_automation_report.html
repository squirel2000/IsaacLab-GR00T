01系統架構

本機 (Windows) 透過 HTTPS 連到 nginx 後方的 Jupyter Server。Jupyter 暴露三個我們會用到的介面： Contents API（檔案）、Kernels + WebSocket（執行程式）、 /files（原始檔案下載，支援續傳）。三者都共用同一組登入 Cookie。

關鍵心智模型

整套自動化只靠三件事：一組登入 Cookie + 一個 _xsrf token + 三個 HTTP/WS 端點。 理解這點，後面所有指令都只是它們的組合。

02探索歷程 · side chat

這一節重現真實的偵錯過程——每一步「為什麼這樣試、結果學到什麼」。展開即可看到當時實際下的指令。

PROBE這到底是什麼服務？用 curl 看 header▶

先不登入，純看 HTTP 回應。發現 301 轉址到 /pegasus/，Server 是 nginx， 且 CSP frame-ancestors 指向 daa.asus.com（內部平台）。

跟著轉址抓內容，HTML <title>Jupyter Server</title> 與密碼表單現形 → 這是 Jupyter Server。

WIN用密碼登入拿到 session cookie▶

Jupyter 登入是兩步：先 GET 拿 _xsrf cookie，再 POST 密碼 + _xsrf。成功回 302 → /pegasus/tree 並種下登入 cookie。詳見 §03。

GOTCHAcurl 對 PUT 上傳 segfault▶

在 sandbox 用 curl -X PUT --data @body.json 上傳時 curl 直接 Segmentation fault。 與其和 curl build 纏鬥，直接改用 Python（後續要交付的也是 Python），更穩也更貼近成品。

GOTCHA/tmp 不一致：bash 的 /tmp ≠ Windows python 的 /tmp▶

Write 寫到 bash 的 /tmp，但 python3 解析到 Windows 版，把 /tmp 當成 %TEMP%，找不到檔案。 結論：在 Windows 上一律走 PowerShell + 明確 Windows 路徑。

GOTCHASSL：self-signed certificate in chain▶

從 Windows 連線時 requests 報 CERTIFICATE_VERIFY_FAILED。檢查憑證鏈發現是 ASUSTEK 2016 Service CA1（內部 CA），不在 Python 的 certifi 信任清單。 解法是 truststore 改用 Windows 信任庫，見 §04。

WIN確認可上傳/下載/執行任意程式▶

完整跑通：list / 上傳（含二進位，MD5 round-trip 吻合）/ 下載 / 刪除 / 透過 kernel WebSocket 執行 shell。 探測到 gallop@pa-jp-v1、/data、Python 3.12、2×H100。

GOTCHA大檔下載：/files 回 403▶

Contents API 用 base64 整檔載入記憶體，對 18GB 不可行。改用原始端點 /files/<path> 卻回 403（被導去登入頁）。 加上 ?_xsrf=<token> 後即通過，且回應帶 Accept-Ranges: bytes → 支援續傳！見 §08。

GOTCHAmonitor 一直 404：Jupyter 隱藏 dot 目錄▶

把狀態檔放在 .pegasus_runs（dot 開頭）→ /files 一律 404，因為 Jupyter 預設 allow_hidden=False。 改用非隱藏目錄 pegasus_runs 立刻正常。

GOTCHAconda 在 bash -lc 找不到；env 是「路徑型」▶

非互動 bash -lc 下 conda: command not found；而且 gr00t_n1d5 不在預設 envs，按名稱 activate 會失敗。 正解：先 eval "$(... conda shell.bash hook)"，再用完整路徑 activate。見 §07。

WIN驗證 detached 工作能在 kernel 被刪後存活▶

關鍵實驗：用 setsid 啟動背景工作後立刻刪掉 kernel，再用 /files 觀察 log——工作仍持續寫到完成。 這證明長時間訓練不會因為斷線/關 kernel 而中斷，是整個設計的基石。

WINselftest 端到端通過▶

用假工作（造 12MB 隨機檔 + 假 checkpoint）跑完整流程：啟動→監控→rm -rf checkpoint-9*（正確保留 100000）→zip→sha256→ 續傳下載→sha256 與大小皆吻合。流程機制全數驗證。

03登入與 XSRF token

Jupyter 的密碼登入是 兩段式：① GET 登入頁讓伺服器種下 _xsrf cookie； ② POST 密碼 + _xsrf。之後所有「會改變狀態」的請求（PUT/POST/DELETE）都要帶 X-XSRFToken header。

用 curl 走一遍（理解原理）

語法意義
-c cj.txt把回應的 Set-Cookie 寫入 cookie jar 檔（--cookie-jar）。
-b cj.txt請求時讀取並送出 cookie jar 內的 cookie（--cookie）。
--data-urlencode把欄位做 URL 編碼後當 POST body；密碼裡的 #、& 等才不會被誤解。
-sS-s 安靜（不顯示進度），-S 但仍顯示錯誤。
-i輸出包含 HTTP 回應標頭（才看得到 302 與 Location）。

Python 版（成品採用）

安全：密碼來源

目前 pegasus.py 頂端用 PEGASUS_PASSWORD 常數帶密碼（方便，但會寫進檔案——本報告已隱去其值）。 若要避免把密碼 commit 進 git，建議留空改用互動輸入（getpass），或改回環境變數。密碼帶日期/_PE 字尾，研判會定期輪替。

06遠端執行：kernel + WebSocket

要在伺服器上跑程式，就建立一個 Python kernel，透過 WebSocket 送出 execute_request 訊息， 再串接回傳的 stream 訊息即可即時看到輸出。我們在 kernel 裡用 subprocess 包一層 bash，等於拿到 shell。

execute_request 訊息結構與串流接收

欄位 / 語法作用
msg_type: execute_request要求 kernel 執行 content.code 內的程式。
parent_header.msg_id回傳訊息會帶上原請求的 msg_id；用它過濾「屬於自己的」訊息。
msg_type: streamstdout/stderr 的即時輸出，可能分多段送達。
status: idle該次執行結束的訊號（執行中為 busy）。
stop_on_error: true遇到例外即停止後續執行。

包成兩個好用的函式：run（串流）與 sh（擷取）

成品把上面流程封裝起來，並在 kernel 內用 subprocess 跑 bash -lc，等於取得遠端 shell； 再用一行哨兵 __PEGASUS_RC__=<code> 把退出碼帶回來。

07Detached 執行：讓訓練不怕斷線

100k steps 的訓練要跑很久，不能靠一直開著 WebSocket。解法是把工作用 setsid 丟進獨立的 session，輸出導向檔案、放到背景；如此即使啟動它的 kernel 被刪、本機斷線，工作仍持續。

進入 conda 環境（兩個坑都在這）

detached 啟動指令逐字拆解

片段意義
: > run.log: 是 no-op，> run.log 把 log 檔清空/建立。
nohup忽略 SIGHUP（掛斷訊號），終端關閉也不會殺掉行程。
setsid在新的 session 啟動行程，脫離原 process group——這是能在 kernel 死後存活的關鍵。
</dev/nullstdin 接空裝置，避免行程因等待輸入而卡住。
>/dev/null 2>&1外層 stdout/stderr 丟棄（真正的日誌由 wrapper 內部寫入 run.log）。2>&1 把 stderr 併入 stdout。
&（單個）放到背景執行，指令立即返回。
echo $! > wrapper.pid$! 是剛背景化行程的 PID；存檔以便日後 stop 用。
為什麼 setsid 後 PID == PGID

setsid 建立的行程是新 session/group 的領導者，PID 即 PGID。要中止整棵行程樹只需對負的 PID 送訊號： kill -TERM -$PID（負號代表整個 process group）。

08續傳下載 + 完整性驗證

checkpoint zip 約 18 GB，下載中途斷線是常態。原始端點 /files/<path>?_xsrf=<token> 支援 Accept-Ranges: bytes，因此可用 HTTP Range 從中斷點續傳，最後再比對大小 + sha256。

探測 Range 支援（決定設計的關鍵一步）

成品的可續傳下載函式

語法意義
Range: bytes=pos-請求從第 pos 個 byte 到結尾；伺服器回 206 Partial Content。
Content-Range: .../TOTAL回應標頭，斜線後是檔案總長度，用來得知 100% 是多少。
open(local, "ab")以二進位附加模式開檔，新資料接在已下載內容後面。
iter_content(chunk)串流分塊讀取，避免整檔載入記憶體。
2 ** attempt指數退避（1,2,4,8…秒，上限 30），避免斷線時狂打伺服器。

09Fine-tuning 全流程

把前面所有概念組起來：run_finetune.py 產生一支 wrapper.sh 上傳到伺服器，detached 執行； 本機只負責監控與下載。每一階段都能在斷線後重新接上。

伺服器端 wrapper.sh（由腳本自動產生）

清理層級：請務必確認

checkpoint 實際在內層 output dir，所以 cleanup 進到 output dir 內執行，並改用 find 依 MAX_STEPS 推導的最終 checkpoint 名稱來保留：只留 checkpoint-100000、刪掉其餘所有 checkpoint-*（不管中間步數編號為何）。改 --max-steps 時只要同步改 MAX_STEPS。selftest 已驗證。

同名舊結果會被覆蓋

伺服器上該 output dir 已存在一次完成的 run（checkpoint-100000 + 18GB zip）。執行 run 會覆蓋它。 要保留請先在 CONFIG 改 output dir 名稱。

10CLI 指令手冊

環境準備（一次性）

pegasus.py — 通用檔案/執行工具

指令說明
python pegasus.py ls [REMOTE_DIR]列出遠端目錄（路徑相對 /data，例如 VLA/experiments）。
python pegasus.py put LOCAL REMOTE上傳檔案或整個資料夾（遞迴，自動建目錄、自動辨識二進位）。
python pegasus.py get REMOTE LOCAL下載檔案或資料夾，檔案走續傳並驗證大小。
python pegasus.py rm REMOTE遞迴刪除。
python pegasus.py mkdir REMOTE_DIR建立目錄。
python pegasus.py run "CMD"遠端執行 bash 指令，即時串流輸出；也可 --file script.sh。

run_finetune.py — Fine-tuning 編排器

指令說明
python run_finetune.py run啟動訓練(detached) → 監控 → 完成後清理+壓縮 → 續傳下載+驗證（一條龍）。
python run_finetune.py monitor斷線後重新接回監控（接著自動下載）。
python run_finetune.py download只重跑下載+驗證（可續傳）。
python run_finetune.py status查看伺服器端目前狀態。
python run_finetune.py stop中止該次 detached 訓練（kill 整個 process group）。
python run_finetune.py selftest用假工作演練整條流程（約 10 秒，不碰真實訓練）。
建議第一次這樣做

① python run_finetune.py selftest 確認連線與流程 → ② 檢視 run_finetune.py 最上方 CONFIG 的指令與路徑 → ③ python run_finetune.py run 正式啟動。啟動後可關掉視窗，日後用 monitor 接回。
